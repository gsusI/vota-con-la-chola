Publicar: tras el push a `main`, desde local (~2,5–3 min; en CI son ~5,5 min). El workflow `Site deploy` (`.github/workflows/site-deploy.yml`) queda solo como respaldo manual (`gh workflow run site-deploy.yml`).

```bash
just site-publish
```

Construye (frozen), toma el cerrojo de publicación en R2 (`locks/site-publish.json`, compartido por CI y sesiones locales), sube a R2 solo lo que R2 sirve, despliega las páginas como static assets del Worker y poda en R2 lo que ya no sirve. Objetivo: ~2–3 min para un cambio de UI. Lo rápido es estructural: el gate escanea solo `ui/site/out` (`just site-artifact-gate`, segundos); el build id de Next solo cambia con el framework (`package-lock.json`; cada cambio implica una resubida completa única de ~4 min), y el runtime de webpack (que lleva el hash de cada chunk JS/CSS) se publica con nombre fijo en `/_next/static/runtime/webpack.js`, servido revalidado y no `immutable` (`scripts/prepare_site_static_assets.py`), así que un cambio de código o de CSS de una sección solo reescribe las páginas que usan ese chunk (tocar `app/citizen/vota/votingAid.css` o `VotingAidClient.js`: ~300 ficheros, 15–60 MB) en vez de los ~1,7k HTML que cargan el runtime (467 MB con el runtime con hash); el CSS global va inline (`experimental.inlineCss`) dos veces en cada HTML (`<style>` y payload RSC) y en cada `__next._index.txt`, así que tocar `app/globals.css` reescribe todas las páginas (~0,5 GB, ~15 min de wrangler, que sube ~0,6 MB/s con 3 peticiones en paralelo fijas): los estilos de una sola sección van en una hoja propia importada desde su `layout.js` (p. ej. `app/citizen/vota/votingAid.css`); R2 no se lista (35k claves) mientras el conjunto que sirve no cambie (huella en `/releases/r2-scope.json`, `--full-sync` la ignora); y las publicaciones encoladas tras el cerrojo de la misma copia de trabajo se saltan si sus entradas (`scripts/site_inputs_fingerprint.sh`) ya están en vivo (`SITE_PUBLISH_FORCE=1` redespliega). Necesita `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` (entorno o `.env`) y, para el Worker, la sesión OAuth de wrangler en local o `CLOUDFLARE_API_TOKEN` (plantilla «Edit Cloudflare Workers») en CI.

`just site-publish` ya despliega el Worker; a mano solo hace falta para cambios de su código:

```bash
just site-origin-worker-deploy
```

Vuelta atrás: del Worker, `wrangler versions deploy <version>@100` desde `infra/cloudflare/votaconlachola-worker/`; del contenido, `git checkout <source_commit>` del manifest de la release buena y `just site-publish` (R2 guarda solo la release actual). Plan gratuito: R2 ≤ 10 GB, escrituras solo de ficheros cambiados, ≤ 19k ficheros estáticos en el Worker.

## SEO (desde `2026-10-22`)

- `ui/site/public/robots.txt` (permite todo, `Content-Signal: search=yes, ai-input=yes`, enlaza el sitemap) y `ui/site/public/llms.txt` (índice para buscadores con IA).
- `sitemap.xml` lo genera `scripts/build_site_sitemap.py` tras `next build` a partir de las páginas exportadas: entra todo `index.html` sin `noindex` cuya canonical sea la propia URL. No hay lista a mano: una página nueva entra sola.
- Metadatos y datos estructurados: `ui/site/app/seo.js`. Toda página indexable usa `pageMetadata({ path, title, description, image })` (canonical + `og:url` + tarjeta coherentes) y, cuando aplica, `JsonLd` con `breadcrumbLd`, `articleLd`, `datasetLd`, `webApplicationLd` o `faqLd` (las respuestas del FAQ deben verse en la página).
- Las páginas que queramos posicionar deben llevar su contenido en el HTML (render en servidor), no solo «Cargando…» en cliente.
- Presupuesto: cada página exportada son ~10 ficheros y el Worker admite ≤ 19k (hoy ~16,4k). Las páginas programáticas nuevas se cuentan contra ese margen.
- Ayuda al voto (`/citizen/vota/`): páginas indexables generadas del snapshot vigente, sin tocar el test: una por partido (`partidos/<slug>/`), una por pregunta clave (`pregunta/<slug>/`, canonical de su `t/<id>/`, que sigue abriendo el juego al compartir) y una por tema (`temas/<slug>/`); slugs y títulos cortos en `app/citizen/vota/votaPaths.mjs`, datos en `votaSeoData.mjs`, piezas en `VotaSeo.js`. Las páginas de cliente (partidos, diputados, votacion, mapa) muestran un resumen en HTML hasta que carga la vista interactiva. Al publicar una versión nueva del test, añade slugs para sus preguntas.
